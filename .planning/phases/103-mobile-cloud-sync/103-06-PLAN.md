<objective>
Build the cloud save layer on top of Plan 05's auth: a 3-slot per-user `CloudSave` collection in Mongo, three new endpoints under `/api/v1/cloudsave/*`, a client-side `outbox` IDB store that drains when online, and a `lastSyncedAt` field added (backward-compatible) to `saveManager.js` slot payloads.

Critical scope clarification per RESEARCH Open Question #2: cloud sync covers ONLY the 3 manual `gogo_save_<n>` localStorage slot files (the user-explicit snapshots). The live Redux/IDB state from Phase 27.1 is single-device-only this phase.

Critical pitfall per RESEARCH Pitfall 4: track TWO local timestamps per slot — `lastSyncedAt` (last successful pull/push) and `lastModifiedAt` (last local change). Conflict exists when `local.lastModifiedAt > local.lastSyncedAt` AND `cloud.lastSyncedAt > local.lastSyncedAt`. Plan 07 builds the conflict UI; Plan 06 builds the detection.

Purpose: SYNC-02 (IndexedDB → cloud push via outbox), SYNC-03 (cloud → IndexedDB pull on boot), SYNC-06 (backward-compatible save migration with lastSyncedAt).

Output: Server endpoints + client outbox + saveManager field extension + 3 test suites (server cloudSave, client outbox, client saveManager migration).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → /api/v1/cloudsave/* | Untrusted save payload up to 256KB; requires auth cookie; zod-validated |
| Mongo per-user data isolation | Every query filtered by req.userId from authenticated cookie; never trust user-supplied userId |
| Client outbox ↔ network | Outbox queue persists offline; drain is idempotent via clientRequestId |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-103-16 | Information Disclosure | Cloud save cross-user leak | mitigate | All endpoints filter by req.userId from authenticated cookie; compound unique index (userId, slot) |
