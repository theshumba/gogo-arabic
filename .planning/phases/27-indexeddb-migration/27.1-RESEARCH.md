# Phase 27.1: IndexedDB Migration - Research

**Researched:** 2026-02-12
**Domain:** Client-side storage migration (localStorage → IndexedDB) with redux-persist hybrid strategy
**Confidence:** HIGH

## Summary

Phase 27.1 addresses the critical localStorage overflow issue before adding new heavy slices in v6.0. Current state: 13 Redux slices persisted to localStorage via redux-persist, with FSRS cards alone approaching 2-3MB for 1,220 words. Upcoming equipment, inventory, companion, and magic slices will push total to 5-10MB, exceeding the 5MB localStorage limit and causing silent save data loss.

Solution: Migrate FSRS cards and battle history to IndexedDB using a custom redux-persist storage adapter, while keeping lightweight slices in localStorage. Use native IndexedDB API (no new dependencies) wrapped with promise-based patterns for easier integration. Implement storage quota monitoring via StorageManager API to warn players at 80% usage.

**Primary recommendation:** Build custom IndexedDB storage adapter implementing redux-persist storage interface (getItem/setItem/removeItem), use hybrid storage strategy (lightweight slices in localStorage, heavy data in IndexedDB), implement one-time auto-migration with redux-persist migrations API, add quota monitoring middleware.

## Standard Stack

### Core
| Library | Version | Purpose | Why Standard |
|---------|---------|---------|--------------|
| IndexedDB API | Native | Client-side structured data storage | Browser-native, no dependencies, 60% of disk quota (vs 5-10MB localStorage), async/non-blocking, ACID transactions |
| redux-persist | 6.0.0 (current) | Redux state persistence | Already in project, supports custom storage adapters, built-in migration API, hybrid storage strategies |
| Native Promise | ES2015+ | Async operations | Required by redux-persist storage interface, native to all modern browsers |

### Supporting
| Library | Version | Purpose | When to Use |
|---------|---------|---------|-------------|
| StorageManager API | Native | Quota estimation and monitoring | Check available space before writes, warn users at 80% usage, request persistent storage for critical data |
| JSON.stringify/parse | Native | Serialization | Redux-persist requires string values, same as localStorage |

### Alternatives Considered
| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| Native IndexedDB | `idb` (promise wrapper) | `idb` is 1.19KB, cleaner API, but adds dependency (violates "no new deps" constraint). Native API is verbose but sufficient for simple get/set/delete operations. |
| Custom adapter | `redux-persist-indexeddb-storage` | Package is 6 years old (last update), uses localforage (47KB), adds 2 dependencies. Custom adapter is 50-100 lines for basic needs. |
| Hybrid storage | All IndexedDB | localStorage is faster (0.017ms vs 0.17ms writes) and synchronous. Keep lightweight slices (settings, ui state) in localStorage for instant reads. |
| redux-persist migrations | Manual migration script | Migrations API handles version checks, rollback on failure, and integrates with persist lifecycle. Manual approach duplicates effort. |

### Pattern 1: Custom IndexedDB Storage Adapter for redux-persist
**What:** Implement storage interface (getItem/setItem/removeItem returning promises) using native IndexedDB API.
**When to use:** When redux-persist needs to store state in IndexedDB instead of localStorage.
**Example:**
```javascript
// Source: Native IndexedDB API + redux-persist storage interface requirements
// src/services/storage/indexedDBAdapter.js

const DB_NAME = 'gogo-arabic-idb';
const DB_VERSION = 1;
const STORE_NAME = 'redux-state';

// Open database connection (reusable)
const openDB = () => {
  return new Promise((resolve, reject) => {
    const request = indexedDB.open(DB_NAME, DB_VERSION);

    request.onerror = () => reject(request.error);
    request.onsuccess = () => resolve(request.result);

    request.onupgradeneeded = (event) => {
      const db = event.target.result;
      if (!db.objectStoreNames.contains(STORE_NAME)) {
        db.createObjectStore(STORE_NAME);
      }
    };
  });
};

// Redux-persist storage interface
const indexedDBStorage = {
  async getItem(key) {
    const db = await openDB();
    return new Promise((resolve, reject) => {
      const transaction = db.transaction([STORE_NAME], 'readonly');
      const store = transaction.objectStore(STORE_NAME);
      const request = store.get(key);

      request.onsuccess = () => resolve(request.result);
      request.onerror = () => reject(request.error);
    });
  },

  async setItem(key, value) {
    const db = await openDB();
    return new Promise((resolve, reject) => {
      const transaction = db.transaction([STORE_NAME], 'readwrite');
      const store = transaction.objectStore(STORE_NAME);
      const request = store.put(value, key);

      request.onsuccess = () => resolve();
      request.onerror = () => reject(request.error);

      transaction.oncomplete = () => db.close();
    });
  },

  async removeItem(key) {
    const db = await openDB();
    return new Promise((resolve, reject) => {
      const transaction = db.transaction([STORE_NAME], 'readwrite');
      const store = transaction.objectStore(STORE_NAME);
      const request = store.delete(key);

      request.onsuccess = () => resolve();
      request.onerror = () => reject(request.error);

      transaction.oncomplete = () => db.close();
    });
  }
};

export default indexedDBStorage;
```

### Pattern 2: Hybrid Storage Strategy with Separate Persist Configs
**What:** Use localStorage for lightweight slices (settings, ui), IndexedDB for heavy data (fsrsCards, battleHistory).
**When to use:** When total state exceeds localStorage quota but some slices are small and benefit from sync access.
**Example:**
```javascript
// Source: redux-persist docs + architectural analysis of slice sizes
// src/store/store.js

import { persistStore, persistReducer } from 'redux-persist';
import storage from 'redux-persist/lib/storage'; // localStorage
import indexedDBStorage from '../services/storage/indexedDBAdapter.js';

// LIGHTWEIGHT slices: localStorage (fast, sync, <1MB total)
const lightweightPersistConfig = {
  key: 'gogo-arabic-light',
  storage, // localStorage
  whitelist: ['player', 'settings', 'ui', 'alphabet', 'npc', 'achievements',
              'dailyGoals', 'grammar', 'narrative', 'quests', 'sync'],
};

// HEAVY slices: IndexedDB (async, large data, >2MB potential)
const heavyPersistConfig = {
  key: 'gogo-arabic-heavy',
  storage: indexedDBStorage,
  whitelist: ['vocabulary', 'battle'],
  // Only persist heavy fields from these slices
};

// Create separate reducers
const lightweightReducer = combineReducers({
  player: playerReducer,
  settings: settingsReducer,
  ui: uiReducer,
  alphabet: alphabetReducer,
  npc: npcReducer,
  achievements: achievementReducer,
  dailyGoals: dailyGoalsReducer,
  grammar: grammarReducer,
  narrative: narrativeReducer,
  quests: questReducer,
  sync: syncReducer,
});

const heavyReducer = combineReducers({
  vocabulary: vocabularyReducer,
  battle: battleReducer,
});

const rootReducer = combineReducers({
  lightweight: persistReducer(lightweightPersistConfig, lightweightReducer),
  heavy: persistReducer(heavyPersistConfig, heavyReducer),
});

export const store = configureStore({
  reducer: rootReducer,
  middleware: (getDefaultMiddleware) =>
    getDefaultMiddleware({
      serializableCheck: {
        ignoredActions: ['persist/PERSIST', 'persist/REHYDRATE'],
      },
    }),
});

export const persistor = persistStore(store);
```

### Pattern 3: One-Time Auto-Migration from localStorage to IndexedDB
**What:** Use redux-persist migrations API to move existing FSRS cards from localStorage to IndexedDB on first load after update.
**When to use:** When changing storage backend for existing users without data loss.
**Example:**
```javascript
// Source: https://github.com/rt2zz/redux-persist/blob/master/docs/migrations.md
// src/services/storage/migrations.js

import { createMigrate } from 'redux-persist';
import storage from 'redux-persist/lib/storage'; // localStorage

const migrations = {
  // Version 0 → 1: Migrate fsrsCards and battleHistory to IndexedDB
  0: async (state) => {
    console.log('[Migration 0→1] Migrating FSRS cards to IndexedDB...');

    // Read old localStorage data
    const oldVocabState = await storage.getItem('persist:vocabulary');
    const oldBattleState = await storage.getItem('persist:battle');

    if (oldVocabState || oldBattleState) {
      const vocab = oldVocabState ? JSON.parse(oldVocabState) : {};
      const battle = oldBattleState ? JSON.parse(oldBattleState) : {};

      // Data is already in state, just needs to be written to IndexedDB
      // redux-persist will handle this automatically with new storage config

      // Clean up old keys from localStorage (optional, saves space)
      await storage.removeItem('persist:vocabulary');
      await storage.removeItem('persist:battle');

      console.log('[Migration 0→1] Migration complete. Data preserved.');
    }

    return state; // State unchanged, storage backend changed
  },
};

export const migrate = createMigrate(migrations, { debug: true });

// Usage in persistConfig:
```

### Pattern 4: Storage Quota Monitoring Middleware
**What:** Redux middleware that checks StorageManager API after persist actions, warns when 80% quota used.
**When to use:** Prevent silent storage failures by alerting users before quota exceeded.
**Example:**
```javascript
// Source: https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/estimate
// src/services/storage/storageQuota.js

export const checkStorageQuota = async () => {
  if (!('storage' in navigator && 'estimate' in navigator.storage)) {
    console.warn('StorageManager API not available');
    return { usage: 0, quota: 0, percentage: 0 };
  }

  try {
    const estimate = await navigator.storage.estimate();
    const percentage = (estimate.usage / estimate.quota) * 100;

    return {
      usage: estimate.usage,
      quota: estimate.quota,
      percentage: percentage.toFixed(2),
    };
  } catch (error) {
    console.error('Storage quota check failed:', error);
    return { usage: 0, quota: 0, percentage: 0 };
  }
};

export const storageQuotaMiddleware = (store) => (next) => async (action) => {
  const result = next(action);

  // Check quota after REHYDRATE (on load) and PERSIST (after state changes)
  if (action.type === 'persist/REHYDRATE' || action.type === 'persist/PERSIST') {
    const quota = await checkStorageQuota();

    if (quota.percentage > 80) {
      console.warn(`Storage usage: ${quota.percentage}% (${quota.usage}/${quota.quota} bytes)`);

      // Dispatch warning to UI
      store.dispatch({
        type: 'ui/showToast',
        payload: {
          message: 'Storage almost full. Consider clearing old data.',
          severity: 'warning',
        },
      });
    }
  }

  return result;
};
```

### Anti-Patterns to Avoid
- **Opening DB connection per operation:** Cache db instance, reuse across operations. Opening is expensive (~10-20ms).
- **Synchronous localStorage fallback in adapter:** If IndexedDB fails, don't silently fall back to localStorage (quota issue remains). Throw error, let user know.
- **Storing entire Redux state in one IndexedDB key:** Break into separate keys per slice (vocabulary, battle) for partial updates.
- **No error handling in setItem:** IndexedDB can fail (quota exceeded, private browsing mode). Wrap in try/catch, show user-facing error.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Promise-based IndexedDB wrapper | Custom wrapper library | Native Promise + async/await | Project constraint: no new dependencies. Native IndexedDB verbose but sufficient for get/set/delete. |
| Storage quota detection | Polling localStorage size | StorageManager.estimate() API | Native API provides accurate quota across all storage (IndexedDB + localStorage + Cache API), not just one type. |
| State migration versioning | Manual version check in code | redux-persist migrations API | Built-in version tracking, rollback on failure, integrates with persist lifecycle. |
| Serialization layer | Custom serializer for IndexedDB objects | JSON.stringify/parse | Redux-persist already uses JSON for localStorage, IndexedDB supports structured clone but JSON keeps parity. |

**Key insight:** IndexedDB's event-based API is complex, but for redux-persist's simple needs (get/set/delete single keys), wrapping in Promises is sufficient. Full-featured wrappers like `idb` or `localforage` are overkill for this use case and violate the "no new dependencies" constraint.

## Common Pitfalls

### Pitfall 1: Silent localStorage Quota Exceeded → Data Loss
**What goes wrong:** localStorage.setItem() fails silently when quota exceeded (no exception in many browsers). Redux-persist writes appear successful but state is not saved. Player refreshes page, loses all progress since last successful save.
**Why it happens:** localStorage quota (5-10MB) is per-origin, shared across all scripts. FSRS cards alone are 2-3MB. Adding equipment, inventory, companion slices pushes total to 5-10MB. Browsers handle quota differently: Safari throws QuotaExceededError, Chrome/Firefox fail silently.
**How to avoid:**
1. Migrate heavy data to IndexedDB BEFORE adding new slices (Phase 27.1 is blocker)
2. Add quota monitoring middleware that checks after every persist action
3. Test in private browsing mode (stricter quotas, ~5MB total)
4. Wrap localStorage.setItem in try/catch, show error toast on quota exceeded
**Warning signs:**
- redux-persist REHYDRATE takes >500ms (reading large state)
- Users report "lost save data after refresh"
- Browser console shows QuotaExceededError (Safari only)

### Pitfall 2: IndexedDB Schema Changes Break Existing Users
**What goes wrong:** Phase 27.1 ships with DB_VERSION = 1, creates 'redux-state' object store. Phase 30 needs second store 'companion-data'. Incrementing DB_VERSION triggers onupgradeneeded, but existing users' data in 'redux-state' is not migrated to new schema, causing state loss.
**Why it happens:** IndexedDB schema changes require manual migration in onupgradeneeded callback. If you only create new stores without preserving old data, existing users lose state. Event fires BEFORE onsuccess, so you can't read old data easily.
**How to avoid:**
1. Design schema upfront to avoid changes (single 'redux-state' store with key-based separation)
2. If schema must change, use versioned migration:
```javascript
request.onupgradeneeded = (event) => {
  const db = event.target.result;
  const oldVersion = event.oldVersion;

  // Version 0→1: Initial schema
  if (oldVersion < 1) {
    db.createObjectStore('redux-state');
  }

  // Version 1→2: Add companion store
  if (oldVersion < 2) {
    db.createObjectStore('companion-data');
    // Migrate existing data if needed
  }
};
```
3. Test upgrade path: seed v1 schema, upgrade to v2, verify data intact
**Warning signs:**
- Users report "lost data after update"
- onupgradeneeded fires but data disappears

### Pitfall 3: Async IndexedDB Breaks Synchronous Redux Selectors
**What goes wrong:** Component calls `selectFsrsCards(state)` expecting immediate data, but state.vocabulary.fsrsCards is empty because IndexedDB hasn't finished loading yet. UI shows "no words learned" flash before data appears.
**Why it happens:** redux-persist rehydrates asynchronously. With localStorage (sync), rehydration is ~10-50ms. With IndexedDB (async), rehydration is ~50-200ms. Components render before REHYDRATE action completes.
**How to avoid:**
1. Use PersistGate component to block render until rehydration complete:
```javascript
import { PersistGate } from 'redux-persist/integration/react';

<Provider store={store}>
  <PersistGate loading={<LoadingScreen />} persistor={persistor}>
    <App />
  </PersistGate>
</Provider>
```
2. Check rehydration status in selectors:
```javascript
const selectFsrsCards = (state) => {
  if (!state._persist?.rehydrated) {
    return {}; // Empty state until loaded
  }
  return state.vocabulary.fsrsCards;
};
```
3. Show loading state in components:
```javascript
const isRehydrated = useSelector(state => state._persist?.rehydrated);
if (!isRehydrated) return <Spinner />;
```
**Warning signs:**
- Components flash "no data" then populate
- Selectors return undefined/empty objects briefly after mount

### Pitfall 4: Opening New DB Connection Per Operation → Performance Degradation
**What goes wrong:** Every getItem/setItem call opens new IndexedDB connection (indexedDB.open()). Opening takes 10-20ms. 100 operations = 1-2 seconds of connection overhead. Game freezes during save/load.
**Why it happens:** Naive adapter implementation opens DB per operation because examples show request.onsuccess inline. No connection pooling or caching. IndexedDB.open() must read DB metadata from disk.
**How to avoid:**
1. Cache DB connection in module scope (safe in single-threaded JS):
```javascript
let dbInstance = null;

const getDB = async () => {
  if (dbInstance) return dbInstance;
  dbInstance = await openDB();
  return dbInstance;
};
```
2. Reuse connection across operations (don't close after each transaction)
3. Only close on page unload or error:
```javascript
window.addEventListener('beforeunload', () => {
  if (dbInstance) dbInstance.close();
});
```
**Warning signs:**
- IndexedDB operations take >100ms each
- Chrome DevTools shows many 'open' events in IndexedDB panel
- Game stutters when saving state

### Pitfall 5: Migration from localStorage Doesn't Handle Corrupted Data
**What goes wrong:** User's localStorage has corrupted FSRS cards (malformed JSON, partial write). Migration reads corrupted data, JSON.parse() throws, entire migration fails, user loses all state.
**Why it happens:** localStorage corruption happens (browser crash during write, disk full, extensions interfering). Migration assumes clean data. One bad card corrupts entire migration.
**How to avoid:**
1. Wrap migration in try/catch, handle corruption gracefully:
```javascript
0: async (state) => {
  try {
    const oldState = await storage.getItem('persist:vocabulary');
    if (!oldState) return state; // No old data, skip migration

    const parsed = JSON.parse(oldState);
    // Validate critical fields exist
    if (!parsed.fsrsCards || typeof parsed.fsrsCards !== 'object') {
      console.error('Corrupted vocabulary state, skipping migration');
      return state; // Use fresh state
    }

    // Attempt to sanitize
    const sanitized = Object.entries(parsed.fsrsCards)
      .filter(([key, card]) => card && card.card && card.log) // Valid cards only
      .reduce((acc, [key, card]) => ({ ...acc, [key]: card }), {});

    return { ...state, vocabulary: { ...state.vocabulary, fsrsCards: sanitized } };
  } catch (error) {
    console.error('Migration failed:', error);
    // Fallback: start fresh
    return state;
  }
}
```
2. Log migration failures to analytics for debugging
3. Provide manual "reset save data" button if migration fails repeatedly
**Warning signs:**
- User reports "game won't load after update"
- Console shows JSON.parse errors
- persist/REHYDRATE action never completes

### Opening IndexedDB with Upgrade Handling
```javascript
// Source: https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API
const DB_NAME = 'gogo-arabic-idb';
const DB_VERSION = 1;

const openDB = () => {
  return new Promise((resolve, reject) => {
    const request = indexedDB.open(DB_NAME, DB_VERSION);

    request.onerror = () => {
      console.error('IndexedDB open failed:', request.error);
      reject(request.error);
    };

    request.onsuccess = () => {
      console.log('IndexedDB opened successfully');
      resolve(request.result);
    };

    request.onupgradeneeded = (event) => {
      const db = event.target.result;
      const oldVersion = event.oldVersion;

      console.log(`Upgrading DB from v${oldVersion} to v${DB_VERSION}`);

      // Create object store if doesn't exist
      if (!db.objectStoreNames.contains('redux-state')) {
        const objectStore = db.createObjectStore('redux-state');
        console.log('Created object store: redux-state');
      }
    };

    request.onblocked = () => {
      console.warn('IndexedDB upgrade blocked by another tab');
    };
  });
};
```

### Checking Storage Quota with Error Handling
```javascript
// Source: https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/estimate
export const checkStorageQuota = async () => {
  // Feature detection
  if (!('storage' in navigator && 'estimate' in navigator.storage)) {
    console.warn('StorageManager API not available (old browser or private mode)');
    return { usage: 0, quota: 0, percentage: 0, available: false };
  }

  try {
    const estimate = await navigator.storage.estimate();
    const usage = estimate.usage || 0;
    const quota = estimate.quota || 0;
    const percentage = quota > 0 ? (usage / quota) * 100 : 0;

    console.log(`Storage: ${(usage / 1024 / 1024).toFixed(2)} MB / ${(quota / 1024 / 1024).toFixed(2)} MB (${percentage.toFixed(1)}%)`);

    return {
      usage,
      quota,
      percentage: percentage.toFixed(2),
      available: true,
      usageMB: (usage / 1024 / 1024).toFixed(2),
      quotaMB: (quota / 1024 / 1024).toFixed(2),
    };
  } catch (error) {
    console.error('Storage quota check failed:', error);
    return { usage: 0, quota: 0, percentage: 0, available: false };
  }
};

// Request persistent storage (prevents eviction)
export const requestPersistentStorage = async () => {
  if (!('storage' in navigator && 'persist' in navigator.storage)) {
    return false;
  }

  try {
    const isPersisted = await navigator.storage.persist();
    console.log(`Persistent storage: ${isPersisted ? 'GRANTED' : 'DENIED'}`);
    return isPersisted;
  } catch (error) {
    console.error('Persistent storage request failed:', error);
    return false;
  }
};
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| All Redux state in localStorage | Hybrid: lightweight in localStorage, heavy in IndexedDB | 2023-2024 | Prevents quota exceeded errors, scales to 100K+ items, better performance (async doesn't block main thread) |
| LocalForage wrapper | Native IndexedDB with promises | 2020-2021 | Reduces dependencies, smaller bundle size, more control over schema |
| Manual localStorage size tracking | StorageManager.estimate() API | 2018 (Chrome 52+, Firefox 57+) | Accurate quota across all storage types, standardized browser API |
| Separate migration scripts | redux-persist migrations API | 2017 (redux-persist v5) | Integrated with persist lifecycle, automatic version checks, safer rollback |

**Deprecated/outdated:**
- **localForage (2014):** 47KB library, abstracts storage layer. Useful for multi-platform apps, but overkill for web-only with IndexedDB. Not deprecated but unnecessary for this project.
- **redux-persist-indexeddb-storage (2017):** Last updated 6 years ago, uses old localForage patterns. Better to build custom adapter with modern APIs.
- **PouchDB/RxDB for Redux:** Over-engineered for simple persistence needs. These are full client-side databases with sync, designed for offline-first apps with complex queries. Redux state is simpler.

## Open Questions

1. **What is optimal object store structure for vocabulary + battle slices?**
   - What we know: Single object store 'redux-state' with keys 'vocabulary', 'battle' is simplest. Alternative: separate stores 'vocabulary-store', 'battle-store' allows independent indexing.
   - What's unclear: Performance difference between single store with 2 large keys vs 2 stores with many small keys.
   - Recommendation: Start with single store (simpler), profile during Phase 29 when adding equipment (3rd heavy slice). If read/write contention, split stores.

2. **Should migration delete old localStorage keys or keep as backup?**
   - What we know: Deleting saves space (5MB localStorage freed). Keeping allows rollback if IndexedDB migration fails.
   - What's unclear: User behavior if migration fails (do they immediately report bug, or keep playing and lose new data?).
   - Recommendation: Keep old localStorage keys for 1 version (v6.0 → v6.1), delete in v6.2. Gives 2-4 week rollback window.

3. **How to handle IndexedDB unavailable (private browsing, old browsers)?**
   - What we know: Private browsing disables IndexedDB in Safari, limits to 0-5MB in Firefox. IE 11 has buggy IndexedDB.
   - What's unclear: Should app refuse to load, or fall back to localStorage with warning?
   - Recommendation: Detect on load, show modal: "Your browser blocks storage. Progress will not save. Use normal browsing mode." Allow play but warn. Don't silently fall back (quota issue remains).

4. **What is safe threshold for storage quota warning?**
   - What we know: 80% is common UX threshold for "almost full" warnings. Browser eviction happens at 100% (varies by browser).
   - What's unclear: Should warning be dismissible, or block actions until user clears data?
   - Recommendation: Show toast at 80% (dismissible), show modal at 95% (requires action: delete old battles, export save, or continue at risk). Never block completely.
