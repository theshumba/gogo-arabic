# Gogo Arabic — Visual Bug Fix: Options Report

_Generated 2026-06-30 by a 10-agent research swarm (4 diagnosis + 5 strategy + 1 synthesis)._

## What's actually wrong

Four separate, unrelated problems are all happening in the same scene. None of them is a "broken game engine" — each is a small, specific mistake in the code or config:

1. **The checkerboard ground.** The desert floor is sand. To make the sand look varied, the code randomly picks one of three sand images for every tile. The problem: those three images are three slightly different shades of tan. So instead of subtle variety you get a random patchwork of mismatched flat colours with hard edges — which reads as a chaotic checkerboard. It's not dithered art or a broken auto-tiler; it's three colours that should match but don't.

2. **Giant rugs.** Every object in the world gets blown up 4x. That multiplier is correct for tiny 16-pixel objects (a rock, a pot), which then land at exactly one tile. But the rug artwork is naturally much bigger in the source file, so 4x makes it 3 tiles wide and 2 tiles tall — dwarfing everything else. The code never asks "how big should this end up?", it just multiplies blindly.

3. **Everything is a different size (player vs NPCs vs buildings).** There are three different, conflicting sizing rules running at once. NPCs and camels get normalised to a clean one-tile size. The player gets *no* sizing rule at all, so it renders at double everyone else. Buildings hit the same blind 4x as the rug and balloon to 5 tiles across. The fix that already exists for one category was simply never applied to the others.

4. **Floating word labels everywhere.** There's an intended feature that floats the Arabic + romanised name over objects to teach vocabulary. But for a new player it shows *all 8 labels at once, permanently, at full strength*, with no proximity rule and no off-switch. Two other label systems in the same game already do the smart thing (only show when you walk up close) — this one doesn't.

The good news: the grass/oasis areas already render correctly and stay untouched by the fixes. All four problems live in the rendering/config code, not in the artwork or the map data.

**Option A (Surgical fix).** Five small, precise edits — each already traced to an exact line number. Collapse the sand to one colour, normalise prop and building sizes, give the player the same sizing rule NPCs already use, and gate the labels. It reuses patterns that already exist elsewhere in your own codebase, so it's low-novelty repair, not invention. An agent can write it and self-check using the existing screenshot harness without you opening the game. The only delicate part is rescaling the player (its head overlay and collision box have to be adjusted to match).

**Option B (Asset swap).** Sounds appealing — "just get nicer, consistent art" — but it falls apart on contact with reality. Your game uses *custom faceless Islamic characters* (12 outfits, 6 head coverings) and teaches *specific named objects* (faanoos, barmeel, dukkaan, etc.). **Option E (AI-generated art).** The one place AI genuinely helps is the sand: a single seamless, properly-dithered sand tile looks nicer than collapsing to one flat colour. A nice *optional polish step*, not a strategy.

# Appendix A — Root-cause diagnoses (from the code)

## Ground tile rendering — desert sand (MapLoader `_renderSandTile`, desert `BIOME_TILESETS` config)
**Confidence:** high | **Fix complexity:** config-one-liner

**Root cause:** Oasis Village is desert biome (zones.js:41). Almost the entire map is SAND. For each interior sand tile, `_renderSandTile` randomly selects one of the THREE desert beach sheets per tile via `Math.floor(tileHash(x,y,42) * sandKeys.length)` (MapLoader.js:764-765), always at frame 6. I extracted frame 6 (the solid-sand center) from each sheet: each is a single FLAT color with no dither, but the three sheets are three DIFFERENT tan colors — beach-tiles-1 RGB(228,166,114), beach-tiles-2 RGB(219,140,106), beach-tiles-3 RGB(211,159,124). So the renderer paints the sand field as 64px flat squares randomly assigned one of 3 mismatched tan shades, with hard tile edges and no blending. That random multi-tone patchwork (scaled 4x by KENMI_SCALE) is what reads as a chaotic 2-tone checkerboard. It is NOT a broken autotiler, NOT a 2-frame alternating fill, and NOT dithered art — it is the intended per-tile 'visual variety' variant-picker combined with color-inconsistent source sheets.

**Quickest fix:** In MapLoader.js BIOME_TILESETS.desert (line 414-418) reduce sandKeys to a single sheet, e.g. sandKeys: ['kenmi-desert-tiles-desert-beach-tiles-1']. This forces all interior sand to one uniform color (variantIdx always 0), eliminating the multi-tone patchwork, and matches the water-border branch which already uses sandKeys[0]. (If a single color looks too flat afterward, optionally recolor the three sheets to share an identical center sand color so the variety stays subtle — but the one-line sandKeys change alone removes the checkerboard.)

## Decoration prop scale — rugs/carpets rendered oversized in MapLoader prop/deco rendering
**Confidence:** high | **Fix complexity:** localized-code

**Root cause:** Props are scaled by a blanket constant `KENMI_SCALE = 4` applied to their RAW SOURCE CROP dimensions, with NO normalization to a target on-screen size — whereas characters ARE normalized to a fixed 64px target. So a prop's on-screen size is entirely a function of how big its crop region is in the source sheet.

The desert-rugs sheet (`public/assets/kenmi/desert/props/desert-rugs.png`) is 96x96 px and is cropped into 6 regions of 48x32 each (PROP_CROP_REGIONS, MapLoader.js:192-199). At KENMI_SCALE=4 each rug renders at 48*4 x 32*4 = 192 x 128 game px. With TILE=64, that is exactly 3 tiles wide x 2 tiles tall.

By contrast, NPCs/player normalize: NPC.js:49-52 computes `setScale(TARGET_DISPLAY / frameWidth)` with TARGET_DISPLAY=64, so every character lands at ~64px (one tile) regardless of source frame size. A typical small prop (rock/pot at 16x16, e.g. desert-pots-sacks.png is 80x16) also lands at 16*4=64px=one tile, so it matches characters — but the inherently large 48x32 rug art, multiplied by the same fixed x4, dwarfs the 64px-normalized characters by ~3x horizontally and 2x vertically. That is the observed "rugs ~3-4x larger than player/NPCs."

There are TWO prop-rendering paths and both have the identical defect: (a) placed objects in loadObjects — `sprite.setScale(KENMI_SCALE)` at MapLoader.js:1519 (cropped) and :1534 (uncropped); (b) procedural scatter `_createDecoSprite` — `sprite.setScale(KENMI_SCALE)` at MapLoader.js:1950. Note path (b) DOES size-normalize for large SINGLE-object images (palm/acacia → setScale(1) at MapLoader.js:1960-1963 because srcW>16), proving the authors knew large source art needs different scaling — but cropped MULTI-item sheet regions (rugs) are unconditionally x4 regardless of the region's pixel size, so the 48x32 rug crop is treated exactly like a 16x16 rock crop.

So the exact mechanism: oversized rug = (48x32 source crop) x (fixed KENMI_SCALE 4) with no per-prop / per-crop target-size normalization. KENMI_SCALE=4 is correct only for 16px-baseline art; the rug art is 3x2 baseline tiles, so x4 makes it 3x2 world tiles.

**Quickest fix:** Normalize prop crop scale to a target tile footprint instead of a blanket x4 — mirror the NPC approach. In both prop paths (MapLoader.js:1519 and :1950), replace `sprite.setScale(KENMI_SCALE)` for cropped regions with a per-prop normalized scale, e.g. add a `PROP_SCALE_OVERRIDES` table keyed by texture key (set 'kenmi-desert-props-desert-rugs' to render at ~1 tile) OR compute `scale = (TARGET_TILES * TILE) / Math.max(region.w, region.h)` so a 48x32 rug fits ~1 tile instead of 3. This is code/data-only (no tile-editor or manual map work), satisfying the near-zero-manual-work constraint. Lowest-effort single-line variant: special-case rugs to `setScale(KENMI_SCALE / 3)` (~64px) at the two setScale call sites, or add them to a small override map consumed by both paths and _createDecoSprite.

- src/game/systems/MapLoader.js:192-199 — desert-rugs crop regions are 48x32 each (6 cells in a 96x96 sheet); 48*4=192px=3 tiles wide, 32*4=128px=2 tiles tall
- src/game/systems/MapLoader.js:1518-1519 — placed-object path: setCrop(region) then unconditional `sprite.setScale(KENMI_SCALE)` with no target-size normalization
- src/game/systems/MapLoader.js:1949-1951 — scatter path `_createDecoSprite`: cropped multi-item sheets always `setScale(KENMI_SCALE)`, displayH = region.h*4

## Character/sprite scale coherence — no single global world scale; three incompatible scaling conventions coexist across object categories.
**Confidence:** high | **Fix complexity:** localized-code

**Root cause:** There is NO single enforced world scale or "target character height." Three mutually inconsistent scaling philosophies run side by side, so each category lands at a different effective pixel size on the 64px tile grid:

(1) "Multiply source by KENMI_SCALE=4" (MapLoader.js:148). This is the de-facto world scale, valid ONLY for genuinely-16px source art. It is applied to sand tiles (783,816), crop-region props (1519), camels/vultures (2165,2236), and — incorrectly — to large native BUILDING images.

(2) "Normalize to an absolute 64px" — this exists in exactly ONE place: NPC.js:49-52 computes setScale(TARGET_DISPLAY(64)/frameWidth). It is source-resolution-independent and targets 64px = 1 tile. Companion extends NPC so inherits it.

(3) "No scaling at all" — Player.js applies NO setScale anywhere; its 128px frame renders native at 128px = 2 tiles. The player is the only character with zero normalization, making it exactly 2x every NPC/camel/companion.

Concrete on-screen sizes I verified from the actual PNGs:
- Player: simple-thobe.png 512x512 / 4x4 grid = 128px frame, no scale -> 128px (2 tiles).
- Camel/NPC: camel-1.png frames are 16px, setScale(4) -> 64px (1 tile) -> half the player. ("camel is small")
- Rug: desert-rugs.png 96x96, crop region 48x32 x4 -> 192x128px (3x2 tiles) -> ~3x an NPC. ("rugs 3-4x larger")
- Building desert-house-1.1.png 80x80 native image, NOT in PROP_CROP_REGIONS, hits the else branch MapLoader.js:1532-1534 which blindly applies setScale(KENMI_SCALE=4) -> 320x320px (5x5 tiles); desert-house-3.1.png 128x112 -> 512x448px. ("building is large")

The building overscale is a true bug, not just relative perception: the deco-scatter path _createDecoSprite (MapLoader.js:1953-1964) already has the correct guard (srcW<=16 -> x4, else native scale(1)), but the main placeObjects loop (1532-1534) lacks it and 4x's everything. So a >16px building image is treated like a 16px tile.

**Quickest fix:** Two localized code edits, zero owner work: (1) In Player.js constructor add the same normalization NPC.js uses — e.g. const fw = scene.textures.get(textureKey)?.get?.(0)?.width || 128; this.setScale(TARGET_DISPLAY/fw) with TARGET_DISPLAY chosen to match characters (use a shared exported constant, not a literal). For the current 128px frame at TARGET 64 that is scale 0.5, making the player equal to NPCs/camels. (2) In MapLoader.js:1532-1534 replace the unconditional setScale(KENMI_SCALE) in the no-crop-region branch with the same source-width guard already present in _createDecoSprite (1953-1964): if source frame width > 16, render near native (scale 1) instead of 4x, so 80-128px building images stop being quadrupled. To make scale coherent long-term, promote a single CHARACTER_TARGET_PX / world TILE (64) constant imported by Player.js, NPC.js, and the building branch so every category derives its scale from one authority instead of three conventions.

**Addresses:** Symptom 3 (checkerboard sand): FULLY — a single AI-generated seamless dithered sand tile is a genuine quality upgrade over the one-line flat-color fix.; Symptom 1 (oversized rugs): PARTIALLY — only if assets are regenerated at a true 16px base AND the code still adds per-crop scale normalization; AI art fed through the same x4 blanket would still be oversized.; Symptom 2 (inconsistent cross-category scale): PARTIALLY — regenerating everything to one base resolution helps, but buildings/player/NPC scale incoherence is a code-convention bug (3 scaling philosophies) that AI assets do not touch.; Symptom 4 (label clutter): NOT ADDRESSED AT ALL — labels are React/Phaser text from FloatingArabicLabelManager, unrelated to assets.; Symptom 5 (don't break what works): AT RISK — regen can make the working grass/oasis/NPC set incoherent with new AI art.

**Pros:** The sand checkerboard (symptom 3) is the one place AI adds real value: a seamless, dithered, palette-coherent sand tile looks markedly better than collapsing to a single flat tan.; PixelLab/Scenario assets ship with commercial licensing you own, removing any dependency on the third-party Kenmi packs long-term.; If all source art were regenerated to one true base resolution, the existing blanket x4 scale would become uniformly valid, indirectly easing the scale-coherence problem.; The project already has a screenshot harness, so an agent can drive a generate-normalize-wire-screenshot loop with little owner input.; Style-reference / private-model training (Scenario, PixelLab Bitforge) can target the existing look, reducing — not eliminating — coherence drift.

**Cons:** Wrong tool for the actual defects: all four bugs are code/config, fixable in ~15 lines total (one is literally a one-line sandKeys change). AI regen is a sledgehammer that still REQUIRES those code fixes to work.; Does nothing for label clutter (symptom 4), the most visually dominant problem.; High style-coherence risk: 2025/2026 AI pixel models are good for single sprites but unreliable at producing 50-100+ sprites that share one palette/outline/lighting convention AND match the retained Kenmi NPCs and palms that already render correctly — likely to RE-introduce incoherence.; Scale is not fixed by art: AI outputs still pass through the same un-normalized x4 crop path, so a 48x32 AI rug is just as oversized as the current one until the code is changed. The art change is cosmetic, not causal.; Downscaling existing 48x32/80x80/128px art to a 16px base to 'normalize' destroys the art; the assets are already at correct relative densities — the renderer, not the art, is wrong.; Cost, accounts, API keys, and per-call billing add operational overhead and a recurring subscription for a problem the code fix solves for free.; Copyright ambiguity: purely AI-generated images have weak/again-uncertain copyright status; style-mimicking the Kenmi pack risks derivative concerns.; Far higher effort and regression surface than the targeted code fixes (Strategies that just edit MapLoader.js/Player.js/WorldScene.js).
